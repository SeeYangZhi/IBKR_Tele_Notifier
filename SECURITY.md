# Security Policy

This project holds credentials to a live brokerage account and can stop a trading gateway. Please read this before deploying it.

## Reporting a vulnerability

**Do not open a public issue for a security problem.** Report it privately through GitHub's [private vulnerability reporting](https://docs.github.com/en/code-security/security-advisories/guidance-on-reporting-and-writing-information-about-vulnerabilities/privately-reporting-a-security-vulnerability) on this repository ("Security" → "Report a vulnerability").

Please include a description of the issue, the affected version or commit, and reproduction steps. Expect an acknowledgement within a few days. This is a small hobby project maintained in spare time — there is no formal SLA, but credential-exposure and privilege-escalation reports get priority.

## What this software can and cannot do

**Cannot place or modify orders.** This is enforced at two independent layers:

1. **IBC** — `ReadOnlyApi=yes` in `config.ini` tells IB Gateway to reject order-placing API calls.
2. **The application** — the code only ever reads (`portfolio()`, `accountValues()`, `fills()`). It imports no order types and calls no order methods.

Neither layer is a substitute for verifying it yourself against a paper account first. Layer 1 is the one that actually binds; layer 2 is a property of code you should read.

**Can stop and restart IB Gateway.** The ops bot shells out to `systemctl` for `ibc-gateway`. Stopping the gateway stops the notifier from seeing anything — a denial-of-visibility, not a trading capability.

## Credentials and where they live

| Secret | Location | Mode | Committed? |
|---|---|---|---|
| Telegram bot tokens, chat ids | `<project>/.env` (and `.env.test`) | `600` | **Never** — gitignored |
| IBKR login and password | `~/ibc/config.ini` on the host | `600` | **Never** — the tracked `deploy/config.ini` template is credential-free |
| VNC password | `~/.vnc/passwd` | `600` | **Never** — generated by `setup.sh` |
| Host, zone, remote path | `deploy/deploy.env` | — | No (gitignored); contains no secrets |

`deploy.sh` never pushes any of these; they are created on the host and stay there.

**Bot tokens are kept out of logs deliberately.** `httpx` and `httpcore` log full request URLs at `INFO`, and a Telegram Bot API URL embeds the token. Both loggers are raised to `WARNING` in `ibkr_telegram_notifier.py` and `ibkr_ops_bot.py`. If you add HTTP logging, do not undo this.

If you believe a credential has leaked: rotate the IBKR password at ibkr.com, revoke the bot token with `/revoke` in @BotFather, and regenerate the VNC password with `x11vnc -storepasswd`.

## Threat model for the ops bot

The ops bot is the most security-relevant component. Understand its two authorization paths before using it.

**Channel posts (`OPS_CHAT_ID`)** are authorized by chat id alone. Telegram channel posts carry no user identity, so the bot cannot tell *which* member posted a command. **Everyone who can post in that channel can run every ops command**, including `/pause` (stops your gateway) and `/positions` (discloses your full portfolio and account value).

> Keep the ops channel private and single-member. Adding a person to it grants them full ops control and full visibility into your positions.

**Direct messages** are authorized against `OPS_ALLOWED_USER_IDS`, an explicit allowlist of numeric Telegram user ids. This is the per-user-secured path; prefer it. An empty allowlist disables DM commands entirely.

**Anyone holding the bot token can impersonate the bot**, but that does not by itself grant ops control — commands are accepted only from the configured channel or allowlisted users. A leaked token does let an attacker read the ops channel's traffic, which includes position snapshots.

### The sudo grant

`setup.sh` installs `/etc/sudoers.d/ibkr-ops-bot`, scoped to exactly the verbs the bot needs:

```
<user> ALL=(root) NOPASSWD: /usr/bin/systemctl start ibc-gateway, \
  /usr/bin/systemctl stop ibc-gateway, \
  /usr/bin/systemctl restart ibc-gateway, \
  /usr/bin/systemctl reset-failed ibc-gateway, \
  /usr/bin/systemctl restart ibkr-notifier, \
  /usr/bin/systemctl restart ibkr-ops-bot, \
  /usr/bin/systemctl restart ibkr-notifier ibkr-ops-bot
```

Nothing here can write to `/etc`. Switching the notifier between the production
and test channel writes `channel.env` inside the project directory, which the
unit loads with `EnvironmentFile=-`, rather than editing a systemd drop-in —
which is why the grant needs no `daemon-reload` and no file-manipulation verbs.

Do **not** replace this with a blanket `NOPASSWD: ALL`. The bot processes input from the internet; a broad grant would turn a Telegram message into root on the host. Command arguments are never interpolated into a shell — `subprocess.run` is called with an argument list and a fixed verb set.

## Network exposure

The intended posture is **zero inbound exposure**:

- **IB Gateway API (`4001`)** binds to `127.0.0.1`. Never expose it. It is an unauthenticated control channel to your brokerage account — anything that can reach the port can talk to it.
- **VNC (`5900`)** runs with `-localhost`, reachable only through an SSH tunnel (`ssh -L 5900:localhost:5900 <host>`). It exists for the one-time Gateway GUI configuration.
- **Outbound only** to `api.telegram.org` and IBKR.

If your host has a public IP, confirm your firewall does not forward `4001` or `5900`.

## Supported versions

Only the latest commit on the default branch receives fixes.
